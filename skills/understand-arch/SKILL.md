# Understand Arch

Produce auditable diagrams from repository evidence. A short request such as “根据代码生成架构图” is sufficient; infer scope, view, engine, and export without requiring a reference image or a detailed prompt. The agent interprets architecture and business meaning; scripts validate source anchors and supported diagram semantics. Keep generated files outside the analyzed repository unless the user asks to commit them. Read [the diagram standard](../../docs/DIAGRAM_STANDARD.md) when selecting a profile. The draw.io landscape theme and GitHub template decision are documented in [the template research](../../docs/ARCHITECTURE_TEMPLATE_RESEARCH.md).

## Workflow

1. Resolve this skill's real directory. The CLI is `../../scripts/generate_architecture.py` relative to that directory. Run `python3 <cli> context --source <repo> --output <workdir>/context.json`. For a relevant symbol discovered in the first pass, repeat `--focus <qualified-method>` to include its CodeGraph callees. Do not create a CodeGraph index on the user's behalf.
2. Inspect the complete context. `files`, `symbols`, `routes`, `configKeys`, and `tables` are never capped; scans are candidates to verify. When `codeGraph` is present, start from its structured classes, routes, and focused calls; use `codegraph explore`/`node` to follow relevant paths. A freshness warning means graph data is only a lead: verify against current source. If `knowledgeGraph` or `domainGraph` exists, use its IDs/flows as navigation and semantic draft, with the same freshness caveat. Graph calls are code facts, not automatically architecture relationships. For a large context, inspect by module without silently discarding modules.
3. Choose a profile before an engine. A short “项目／模块架构图” request defaults to `architecture-landscape`: show supported entrances, the actual module boundary, major services, data facilities, and external systems. This is a readable architecture overview convention, not an official C4 diagram. Use C4 context/container/component when the user specifically asks for C4 or a particular C4 level. Business steps use BPMN, call chronology UML sequence, table relations ERD. Write one `<workdir>/architecture-ir.json` per view using [typed IR v2](references/diagram-view-ir.md). Keep IR v1 for [legacy artifacts](references/architecture-ir.md). Cite exact source path, one-based line, and verbatim substring for every element and relation. Mark a claim `EXTRACTED` only when its visible name or relation label occurs literally in cited source; translated names and architectural interpretations are `INFERRED`, unresolved claims `AMBIGUOUS`. For a new landscape overview, record omitted source-backed candidates in `coverage.omitted`, with evidence and a nearby detail IR containing each omitted element or relation; use an empty list when there are none. Do not dump every class, table, or CodeGraph edge onto an architecture canvas. Do not infer a gateway, replica database, cache, or future/planned component merely because one appears in an example image.
4. Run `python3 <cli> validate --source <repo> --ir <workdir>/architecture-ir.json`. Repair the reported assertions and validate again. A new landscape overview needs `coverageCheck: pass`; `not_declared` only preserves older files. Never remove a rejected assertion silently. If a supported interpretation cannot be established, keep it `AMBIGUOUS` and explain the limitation to the user.
5. Select only an engine supported by the profile. For an unspecified destination, prefer editable draw.io plus PNG for `architecture-landscape`, C4 and BPMN, PlantUML plus PNG for sequence, and Mermaid plus PNG for ERD. `architecture-landscape` currently targets draw.io only. Draw.io also supports the current UML sequence subset when requested; its editor has broader UML capabilities than this adapter. Mermaid C4 is experimental; disclose that status if explicitly chosen. Run `python3 <cli> render --source <repo> --ir <workdir>/architecture-ir.json --output <workdir>/architecture --format <chosen> --export-for <chosen>:png`. Repeat `--format` only for requested additional engines. Export support remains Mermaid/PlantUML `svg|png|pdf`, draw.io `svg|png|jpg|pdf`, and legacy Archify `svg|png|jpg|webp|webm|pdf`. The CLI rejects unsupported profile/engine combinations; do not substitute a generic flowchart and claim the requested notation. A requested export succeeds only when listed in `artifacts`. `rendererChecks` proves official syntax/export, not diagram semantics or visual quality; without an official engine it is `skipped` or fails when required.
6. Open the exported image. Check title, legend, scope, typed elements, arrow direction, label readability, overlap, and unexplained IDs. The landscape validator rejects more than 12 elements or 12 relations and labels that exceed card/register limits. When it rejects a view, preserve all source-backed claims in the IR and make a concise overview plus one or more focused detail views; never drop a relation merely to satisfy the cap. Route kinds `primary`, `secondary`, and `dependency` are editorial classifications requiring source evidence and review. Report visual review separately from `rendererChecks`. The first FA architecture version failed here despite valid source files; the skill must not repeat that delivery error.

## Official native diagrams outside IR v2

Read [the renderer capability audit](../../docs/RENDERER_CAPABILITY_AUDIT.md) and [the native authoring contract](references/native-diagrams.md) when the user requests another diagram type supported by Mermaid, PlantUML, draw.io, or Archify. For an existing native `.mmd`, `.puml`, `.drawio`, or Archify `.json`, run `python3 ../../scripts/render_native_diagram.py --engine <engine> --input <file> --output <dir> --export png` (repeat `--export` for desired formats). The command runs the actual official engine; Archify accepts all five official typed modes.

For a **new** diagram outside IR v2, first choose the notation that answers the user's question, then inspect the relevant code, author the official native syntax, and run the same command. If the diagram makes repository claims, write a [version 2 evidence manifest](references/native-diagrams.md) linking every material native statement to exact source lines. Add `--source-repo <repo> --evidence <manifest>`; a missing claim or invalid anchor fails before export. Review every `INFERRED` and `AMBIGUOUS` claim, open the rendered image, and correct layout or meaning before delivery. `sourceEvidence: anchors_validated` and `claimCoverage: complete` mean each inventoried material item has a source quote; `claimSemantics: not_proven` means the CLI has not proven the interpretation. Without the manifest, the receipt says `sourceEvidence: not_checked`. Prefer typed IR where it already supports the requested diagram. Do not invent a finite draw.io type catalog or call official syntax validation semantic proof.

The source-line check proves that a cited snippet exists at that location. It does not prove a business interpretation, runtime route, or relationship. Review `INFERRED` and `AMBIGUOUS` claims against multiple code paths before presenting them as conclusions.
